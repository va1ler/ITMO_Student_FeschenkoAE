## §1. Что ты уже умеешь и чего не хватает

В ЛР1 у тебя был один класс `Main`, и все методы были `static`. Данные лежали в переменных и массивах, методы получали их через параметры. Это называется **процедурный стиль**: отдельно данные, отдельно функции.

Попробуем так описать трёх покемонов: у каждого имя, здоровье (HP) и атака.

```java
public class Main {
    public static void main(String[] args) {
        String[] names = {"Пикачу", "Бульбазавр", "Чармандер"};
        int[] hp = {35, 45, 39};
        int[] attack = {55, 49, 52};

        for (int i = 0; i < names.length; i++) {
            System.out.println(names[i] + ": " + hp[i] + " HP, атака " + attack[i]);
        }
    }
}
```
Вывод:
```
Пикачу: 35 HP, атака 55
Бульбазавр: 45 HP, атака 49
Чармандер: 39 HP, атака 52
```

Работает, но представь, что дальше:
- у покемона 6 характеристик, тип, до 4 атак, уровень. Это 10+ массивов, и номер `i` должен совпадать во всех. Ошибёшься в одном — Пикачу получит атаку Чармандера;
- чтобы передать одного покемона в метод, нужно передать 10 параметров;
- атаки тоже разные: одна парализует, другая повышает скорость. Куча `if` по номеру атаки.

**Идея ООП:** сделать свой **тип данных** «Покемон», в котором всё про одного покемона лежит вместе. Тогда одна переменная = один покемон целиком.

`int` — тип для чисел, `String` — тип для текста. В ООП ты сам создаёшь новые типы: `Monster`, `Move`, `Battle`. Создаются они словом `class`.

## §2. Класс и объект

**Класс** — это чертёж, или бланк анкеты: какие поля у неё есть. **Объект** — одна заполненная анкета. По одному чертежу можно сделать сколько угодно объектов.

Пишем класс `Monster` (не `Pokemon`, чтобы не путать с библиотекой из лабы):

```java
public class Main {
    public static void main(String[] args) {
        Monster a = new Monster();   // создали объект
        a.name = "Пикачу";           // заполнили его поля
        a.hp = 35;
        a.attack = 55;

        System.out.println(a.name + ": " + a.hp + " HP, атака " + a.attack);
    }
}

class Monster {        // чертёж: у каждого монстра будут эти три поля
    String name;
    int hp;
    int attack;
}
```
Вывод:
```
Пикачу: 35 HP, атака 55
```

Разбираем по словам:
- `class Monster { ... }` — описали новый тип. Переменные внутри класса (`name`, `hp`, `attack`) называются **полями**.
- `Monster a` — переменная `a` типа `Monster`. Так же, как `int x`.
- `new Monster()` — **создать объект** по чертежу. Без `new` объекта нет.
- `a.name` — точка означает «у этого объекта». `a.name = "Пикачу"` — записать в поле `name` объекта `a`.

**Поля заполняются значениями по умолчанию.** Если поле не заполнить, в нём будет: число — `0`, `boolean` — `false`, `double` — `0.0`, `String` и любой объект — `null` («ничего»).

```java
public class Main {
    public static void main(String[] args) {
        Monster m = new Monster();
        System.out.println(m.name);
        System.out.println(m.hp);
    }
}

class Monster {
    String name;
    int hp;
}
```
Вывод:
```
null
0
```
Сравни с ЛР1: **локальная** переменная внутри метода без значения — это ошибка компиляции (`int k; System.out.println(k);` не скомпилируется). А **поле** без значения — нормально, там 0 или `null`.

## §3. Методы объекта (без `static`)

В ЛР1 все методы были `static`, и всё нужное они получали через параметры. Теперь новое: метод **внутри класса `Monster` без слова `static`**. Такой метод вызывается **у конкретного объекта** и видит **его поля** напрямую.

```java
public class Main {
    public static void main(String[] args) {
        Monster a = new Monster();
        a.name = "Пикачу";
        a.hp = 35;
        Monster b = new Monster();
        b.name = "Чармандер";
        b.hp = 39;

        a.printInfo();     // printInfo работает с полями a
        b.printInfo();     // а тут с полями b
    }
}

class Monster {
    String name;
    int hp;

    void printInfo() {                       // нет static!
        System.out.println(name + ": " + hp + " HP");
    }
}
```
Вывод:
```
Пикачу: 35 HP
Чармандер: 39 HP
```
Внутри `printInfo` написано просто `name`. Это поле **того объекта, у которого вызвали метод**: при `a.printInfo()` это `a.name`, при `b.printInfo()` — `b.name`.

Методы могут принимать параметры и возвращать значения, как в ЛР1:

```java
public class Main {
    public static void main(String[] args) {
        Monster a = new Monster();
        a.name = "Пикачу";
        a.hp = 35;

        a.takeDamage(10);
        System.out.println(a.hp);
        System.out.println(a.isAlive());
        a.takeDamage(30);
        System.out.println(a.hp);
        System.out.println(a.isAlive());
    }
}

class Monster {
    String name;
    int hp;

    void takeDamage(int damage) {     // получить урон: уменьшить СВОЁ здоровье
        hp = hp - damage;
    }

    boolean isAlive() {               // жив ли: вернуть true/false
        return hp > 0;
    }
}
```
Вывод:
```
25
true
-5
false
```

Метод может принимать **другой объект**. Вот монстр бьёт другого монстра:

```java
public class Main {
    public static void main(String[] args) {
        Monster a = new Monster();
        a.name = "Пикачу";
        a.hp = 35;
        a.attack = 15;
        Monster b = new Monster();
        b.name = "Чармандер";
        b.hp = 39;
        b.attack = 12;

        a.hit(b);
        b.hit(a);
    }
}

class Monster {
    String name;
    int hp;
    int attack;

    void hit(Monster other) {
        other.hp = other.hp - attack;   // attack — МОЁ поле, other.hp — поле соперника
        System.out.println(name + " бьёт " + other.name + ", у того осталось " + other.hp);
    }
}
```
Вывод:
```
Пикачу бьёт Чармандер, у того осталось 24
Чармандер бьёт Пикачу, у того осталось 23
```

**Как отличить, когда `static`, а когда нет:**
| | static-метод (как в ЛР1) | метод объекта (без static) |
|---|---|---|
| как вызывать | `Main.square(3)` или просто `square(3)` | `a.printInfo()` — обязательно у объекта |
| видит поля объекта | нет, объекта нет | да, поля того, у кого вызвали |
| пример | `Math.sqrt(2)` | `a.takeDamage(10)` |

## §4. Переменная хранит не объект, а ссылку

Самое важное и самое коварное место. Переменная `int x = 5` хранит само число 5. А переменная `Monster a` хранит **ссылку** — адрес, где в памяти лежит объект. Как контакт в телефоне: в контакте не сам человек, а его номер.

```
  переменные (стек)          объекты (куча)
  ┌─────────┐
  │ a  ●────┼────────►  ┌──────────────────┐
  └─────────┘           │ name = "Пикачу"  │
  ┌─────────┐           │ hp   = 35        │
  │ b  ●────┼────────►  └──────────────────┘
  └─────────┘
```

Если написать `Monster b = a;`, копируется **адрес**, а не объект. Теперь `a` и `b` — два контакта одного и того же человека.

```java
public class Main {
    public static void main(String[] args) {
        Monster a = new Monster();
        a.hp = 35;
        Monster b = a;          // b указывает на ТОТ ЖЕ объект
        b.hp = 1;
        System.out.println(a.hp);
    }
}

class Monster {
    int hp;
}
```
Вывод:
```
1
```
Поменяли через `b`, а изменилось и у `a`, потому что объект один. С массивами в ЛР1 было то же самое: массив — тоже ссылочный тип.

**`null`** — ссылка «в никуда». Если вызвать метод или взять поле у `null`, программа упадёт с ошибкой **`NullPointerException`** (самая частая ошибка в Java).

```java
public class Main {
    public static void main(String[] args) {
        Monster m = null;
        System.out.println(m == null);
        m = new Monster();
        System.out.println(m == null);
    }
}

class Monster {
    int hp;
}
```
Вывод:
```
true
false
```

**`==` у объектов сравнивает адреса**, то есть «это один и тот же объект?», а не «одинаковые ли поля».

```java
public class Main {
    public static void main(String[] args) {
        Monster a = new Monster();
        a.hp = 10;
        Monster b = new Monster();
        b.hp = 10;
        Monster c = a;
        System.out.println(a == b);   // разные объекты, хоть поля и равны
        System.out.println(a == c);   // один объект
    }
}

class Monster {
    int hp;
}
```
Вывод:
```
false
true
```
Строки (`String`) — тоже объекты. Поэтому строки сравнивают через `s1.equals(s2)`, а не `==`.

**Объект в методе.** В ЛР1 ты узнал: метод получает **копию** значения. Для объекта копируется **адрес**. Поэтому метод может менять поля переданного объекта (адрес ведёт к тому же объекту), но если внутри метода переменной присвоить новый объект, снаружи ничего не изменится.

```java
public class Main {
    public static void main(String[] args) {
        Monster m = new Monster();
        m.hp = 10;
        change(m);
        System.out.println(m.hp);
        replace(m);
        System.out.println(m.hp);
    }

    static void change(Monster x) {
        x.hp = 99;              // меняем поле объекта по адресу — видно снаружи
    }

    static void replace(Monster x) {
        x = new Monster();      // x теперь указывает на новый объект
        x.hp = 0;               // меняем НОВЫЙ объект, старый не тронут
    }
}

class Monster {
    int hp;
}
```
Вывод:
```
99
99
```

## §5. Конструктор: заполняем объект сразу при создании

Неудобно после каждого `new` писать три строки `a.name = ...`, легко что-то забыть. **Конструктор** — специальный метод, который сам выполняется при `new`.

Правила конструктора:
1. Имя **точно как у класса**.
2. **Нет** типа возврата, даже `void`.
3. Вызывается только через `new`.

```java
public class Main {
    public static void main(String[] args) {
        Monster a = new Monster("Пикачу", 35);     // значения уходят в конструктор
        Monster b = new Monster("Чармандер", 39);
        System.out.println(a.name + " " + a.hp);
        System.out.println(b.name + " " + b.hp);
    }
}

class Monster {
    String name;
    int hp;

    Monster(String name, int hp) {   // конструктор
        this.name = name;            // поле name объекта = параметр name
        this.hp = hp;
    }
}
```
Вывод:
```
Пикачу 35
Чармандер 39
```

**Что такое `this`.** `this` — ссылка на «этот объект», который сейчас создаётся (или у которого вызван метод).

Зачем он тут: параметр называется `name`, и поле называется `name`. Внутри конструктора просто `name` — это **параметр** (он «ближе», он перекрывает поле). Чтобы сказать «поле», пишем `this.name`.

Частая ошибка — забыть `this`:

```java
public class Main {
    public static void main(String[] args) {
        Monster a = new Monster("Пикачу");
        System.out.println(a.name);
    }
}

class Monster {
    String name;
```

## §6. `private` и инкапсуляция

Сейчас кто угодно может написать `a.hp = -1000` или `a.attack = 999999`. Объект беззащитен. Решение — закрыть поля словом **`private`**: такое поле видно **только внутри своего класса**. Снаружи с ним можно работать только через методы, а методы уже проверяют, что всё корректно.

```java
public class Main {
    public static void main(String[] args) {
        Monster m = new Monster("Пикачу", 35);
        m.hp = -1000;
    }
}

class Monster {
    private String name;
    private int hp;

    Monster(String name, int hp) {
        this.name = name;
        this.hp = hp;
    }
}
```
Ошибка компиляции: `hp has private access in Monster` — «у `hp` закрытый доступ».

Как тогда узнать здоровье? Сделать **геттер** — метод, который возвращает значение поля. А менять — через методы, которые следят за правилами:

```java
public class Main {
    public static void main(String[] args) {
        Monster m = new Monster("Пикачу", 35);
        m.takeDamage(50);
        System.out.println(m.getName() + ": " + m.getHp());
    }
}

class Monster {
    private String name;
    private int hp;

    Monster(String name, int hp) {
        this.name = name;
        this.hp = hp;
    }

    String getName() {          // геттер: только прочитать
        return name;
    }

    int getHp() {
        return hp;
    }

    void takeDamage(int damage) {
        hp = hp - damage;
        if (hp < 0) {           // объект сам следит, чтобы HP не ушло в минус
            hp = 0;
        }
    }
}
```
Вывод:
```
Пикачу: 0
```

Это и есть **инкапсуляция**: объект прячет своё устройство (поля) и сам отвечает за то, чтобы его данные были правильными. Снаружи — только понятные методы.

**Модификаторы доступа** (кто может обращаться к полю или методу):
| Слово | Кто видит | Пример |
|---|---|---|
| `private` | только свой класс | поля `Pokemon` в библиотеке |
| *(ничего не писать)* | свой класс и классы того же **пакета** (§16) | всё, что мы пишем в одном файле |
| `protected` | свой пакет + **наследники** (§8, §11) | `setType`, `addMove` у `Pokemon` |
| `public` | все | `Battle.go()`, `setStats` |

Запоминалка: сверху вниз доступ шире.

**В лабе:** все поля `Pokemon` — `private`. Ты не пишешь `p.hp = 100`, ты вызываешь методы: `setStats(...)`, `setType(...)`. Это инкапсуляция в чистом виде.

## §7. `static`: общее для класса, а не для объекта

В ЛР1 все методы были `static`, потому что объектов не было. Теперь разница стала важна.

- **Без `static`** (поле или метод объекта): у **каждого объекта своё**. У Пикачу своё `hp`, у Чармандера своё.
- **`static`**: **одно на весь класс**, общее для всех объектов. Существует даже если объектов ни одного.

Пример: счётчик созданных монстров. Он должен быть общий, а не у каждого свой.

```java
public class Main {
    public static void main(String[] args) {
        System.out.println(Monster.count);
        Monster a = new Monster("Пикачу");
        Monster b = new Monster("Чармандер");
        Monster c = new Monster("Иви");
        System.out.println(Monster.count);
    }
}

class Monster {
    static int count = 0;      // одно на весь класс
    String name;               // у каждого объекта своё

    Monster(String name) {
        this.name = name;
        count++;               // каждый новый монстр увеличивает ОБЩИЙ счётчик
    }
}
```
Вывод:
```
0
3
```
К static-полю обращаются через **имя класса**: `Monster.count`, как `Math.PI`.

**Правила static-метода:**
- вызывается через имя класса: `Math.sqrt(2)`, `Monster.getCount()`;
- внутри **нет `this`**: метод не знает, «какой объект», поэтому не может просто так обратиться к полям объекта (`name`, `hp`).

Отсюда ответ, почему `main` — `static`: программа только запустилась, объектов ещё нет, и JVM должна вызвать `main`, ни одного объекта не создавая. Поэтому внутри `main` мы и создаём объекты через `new`.

⚠️ На репетиции защиты ЛР1 ты сказал «static — данные не меняются». Это неправильно. «Не меняется» — это `final` (§13). `static` = **принадлежит классу**, а не объекту. Static-поле можно менять (счётчик выше меняется).

Ошибка, которую ты точно встретишь:

```java
public class Main {
    int score = 0;

    public static void main(String[] args) {
        score = 10;
    }
}
```
Ошибка: `non-static variable score cannot be referenced from a static context` — «к нестатическому полю нельзя обратиться из статического метода». У `main` нет объекта, а `score` есть только у объекта.

## §8. Наследование: `extends`

Главная тема лабы. В твоём варианте Golett эволюционирует в Golurk. Golurk умеет всё, что Golett (тот же тип, те же атаки), плюс новую атаку и другие характеристики. Писать всё заново — глупо. **Наследование** позволяет сказать: «новый класс — это старый класс плюс кое-что».

```java
class Charmeleon extends Charmander { ... }
```
читается: «Чармелеон **расширяет** Чармандера», то есть **является** Чармандером и получает всё его.

Слова: класс, от которого наследуются, — **родитель** (предок, суперкласс). Новый класс — **потомок** (наследник, подкласс).

```java
public class Main {
    public static void main(String[] args) {
        Charmeleon c = new Charmeleon();
        c.name = "Огонёк";
        c.roar();          // метод достался от Monster
        c.burn();          // свой метод
    }
}

class Monster {
    String name;

    void roar() {
        System.out.println(name + " рычит");
    }
}

class Charmeleon extends Monster {
    void burn() {
        System.out.println(name + " жжёт огнём");   // поле name тоже унаследовано
    }
}
```
Вывод:
```
Огонёк рычит
Огонёк жжёт огнём
```

Что наследуется:
- все поля и методы родителя, кроме `private`. `private`-поля в объекте потомка **есть** (там хранятся данные), но обращаться к ним напрямую потомок не может, только через методы родителя;
- **конструкторы не наследуются**. Это важно, смотри ниже.

У класса **только один** родитель: `class A extends B, C` не бывает. Но цепочка может быть длинной: `Florges extends Floette extends Flabebe extends Pokemon`. А все классы в Java в самом верху наследуются от класса `Object`, даже если ты не написал `extends`.

### Конструктор потомка и `super(...)`

Объект потомка — это «родитель + добавка». Сначала должна отработать часть родителя, потом часть потомка. Поэтому **первая строка конструктора потомка — вызов конструктора родителя: `super(...)`**.

```java
public class Main {
    public static void main(String[] args) {
        Charmeleon c = new Charmeleon("Огонёк", 16);
        System.out.println(c.name + ", уровень " + c.level + ", огонь " + c.fire);
    }
}

class Monster {
    String name;
    int level;

    Monster(String name, int level) {
        this.name = name;
        this.level = level;
    }
}

class Charmeleon extends Monster {
    int fire;

    Charmeleon(String name, int level) {
        super(name, level);   // сначала родитель заполнит name и level
        fire = 80;            // потом своё
    }
}
```
Вывод:
```
Огонёк, уровень 16, огонь 80
```

Если `super(...)` не написать, Java сама вставит `super()` **без аргументов**. А у `Monster` выше нет конструктора без аргументов, и будет ошибка:

```java
public class Main {
    public static void main(String[] args) {
    }
}

class Monster {
    String name;

    Monster(String name) {
        this.name = name;
    }
}

class Charmeleon extends Monster {
    Charmeleon(String name) {
        this.name = name;
    }
}
```
Ошибка: `constructor Monster in class Monster cannot be applied to given types`. Лечится строкой `super(name);` первой в конструкторе `Charmeleon`.

**В лабе это так:** у `Pokemon` единственный конструктор `Pokemon(String name, int level)`. Поэтому **каждый** твой покемон начинается с `super(name, level);`.

### В каком порядке всё создаётся

`new Charizard()` при цепочке `Monster → Charmeleon → Charizard`: конструктор `Charizard` первой строкой зовёт `Charmeleon`, тот зовёт `Monster`. Тела выполняются **от самого старшего предка к потомку**:

```java

    public static void main(String[] args) {
        new Charizard();
    }
}

class Monster {
    Monster() {
        System.out.println("1. Monster");
    }
}

class Charmeleon extends Monster {
    Charmeleon() {
        super();
        System.out.println("2. Charmeleon");
    }
}

    Charizard() {
        super();
        System.out.println("3. Charizard");
    }
}
```
Вывод:
```

2. Charmeleon
3. Charizard
```

### Главный фокус лабы: потомок добавляет только новое

Родитель в конструкторе выдал атаки. Потомок вызывает `super(...)`, и эти атаки у него уже есть. Ему остаётся добавить **только новую**. Покажем на массиве строк вместо настоящих атак:

```java
public class Main {
    public static void main(String[] args) {
        Charmeleon c = new Charmeleon("Огонёк");
        c.printMoves();
    }
}

class Monster {
    String name;
    String[] moves = new String[4];
    int moveCount = 0;

    Monster(String name) {
        this.name = name;
    }

    void addMove(String move) {
        moves[moveCount] = move;
        moveCount++;
    }

    void printMoves() {
        System.out.print(name + ":");
        for (int i = 0; i < moveCount; i++) {
            System.out.print(" " + moves[i]);
        }
        System.out.println();
    }
}

class Charmander extends Monster {
    Charmander(String name) {
        super(name);
        addMove("Царапка");
        addMove("Угольки");
    }
}

class Charmeleon extends Charmander {
    Charmeleon(String name) {
        super(name);           // тут Charmander уже добавит Царапку и Угольки
        addMove("Огнемёт");    // добавляем только новое
    }
}
```
Вывод:
```
Огонёк: Царапка Угольки Огнемёт
```
В твоей лабе ровно так же: `Golurk` вызывает `super(name, level)`, получает три атаки `Golett`, и добавляет одну `addMove(new FlashCannon())`.

## §9. Переопределение методов (`@Override`)

Потомок может не только добавить новый метод, но и **заменить** унаследованный своей версией. Это **переопределение** (override). Нужно написать метод с **тем же именем и теми же параметрами**.

```java
public class Main {
    public static void main(String[] args) {
        Monster m = new Monster();
        Pikachu p = new Pikachu();
        m.sound();
        p.sound();
    }
}

class Monster {
    void sound() {
        System.out.println("...");
    }
}

class Pikachu extends Monster {
    @Override
    void sound() {
        System.out.println("Пика-пика!");
    }
}
```
Вывод:
```
...
Пика-пика!
```

**`@Override`** — пометка для компилятора: «я переопределяю метод родителя, проверь». Если ты ошибся в имени (`Sound` вместо `sound`) или в параметрах, без `@Override` получится просто **новый** метод, и ничего не сработает, а ты будешь долго искать ошибку. С `@Override` компилятор сразу скажет:

```java
public class Main {
    public static void main(String[] args) {
    }
}

class Monster {
    void sound() {
        System.out.println("...");
    }
}

class Pikachu extends Monster {
    @Override
    void Sound() {
        System.out.println("Пика-пика!");
    }
}
```
Ошибка: `method does not override or implement a method from a supertype` — «метод ничего не переопределяет». **В лабе ставь `@Override` над каждым переопределённым методом.**

**`super.метод()`** — вызвать версию **родителя** внутри своей. Нужно, когда хочешь не заменить, а дополнить:

```java
public class Main {
    public static void main(String[] args) {
        new Pikachu().info();
    }
}

class Monster {
    void info() {
        System.out.println("Я монстр");
    }
}

class Pikachu extends Monster {
    @Override
    void info() {
        super.info();                        // сначала то, что делал родитель
        System.out.println("И я электрический");
    }
}
```
Вывод:
```
Я монстр
И я электрический
```

**Перегрузка и переопределение — не путай** (спрашивают на защите):
| | Перегрузка (overload) | Переопределение (override) |
|---|---|---|
| что это | несколько методов с **одним именем, разными параметрами** | потомок пишет **свою версию** метода родителя |
| где | обычно в одном классе | в потомке |
| параметры | разные | **те же самые** |
| пример | твои `fun(int,int,int)` и `fun(double,double,double)` | `sound()` у `Pikachu` |
| кто выбирает версию | компилятор, по типам аргументов | JVM во время работы, по реальному объекту (§10) |

## §10. Полиморфизм

Слово страшное, идея простая. Переменная типа **родителя** может хранить объект **потомка**: Golurk **является** покемоном, значит его можно положить в переменную типа `Pokemon`.
```java
Monster m = new Pikachu();   // законно: Пикачу является монстром
```
И когда вызываешь метод, выполняется версия **настоящего класса объекта**, а не типа переменной:

```java
public class Main {
    public static void main(String[] args) {
        Monster[] team = {new Pikachu(), new Charmander(), new Monster()};
        for (int i = 0; i < team.length; i++) {
            team[i].sound();     // один и тот же вызов, а работает по-разному
        }
    }
}

class Monster {
    void sound() {
        System.out.println("...");
    }
}

class Pikachu extends Monster {
    @Override
    void sound() {
        System.out.println("Пика!");
    }
}

class Charmander extends Monster {
    @Override
    void sound() {
        System.out.println("Чар!");
    }
}
```
Вывод:
```
Пика!
Чар!
...
```

Вот это и есть **полиморфизм** («много форм»): один и тот же вызов `team[i].sound()` ведёт себя по-разному в зависимости от того, какой объект на самом деле лежит в ячейке.

**Зачем это нужно, на примере лабы.** Класс `Battle` написали в 2018 году. Он ничего не знает про твои `Golurk` и `Thunder`. Он хранит покемонов как `Pokemon`, а атаки как `Move`, и просто вызывает у атаки её методы. Но выполняются **твои** версии этих методов. Так старая библиотека работает с кодом, написанным тобой. Это хороший пример для защиты.

**Два правила, которые надо понимать:**
1. **Компилятор** смотрит на тип **переменной** и проверяет, есть ли такой метод вообще.
2. **JVM** во время работы смотрит на **настоящий объект** и выбирает его версию метода.

Из правила 1: через переменную типа родителя нельзя вызвать метод, который есть только у потомка:

```java
public class Main {
    public static void main(String[] args) {
        Monster m = new Pikachu();
        m.thunder();
    }
}

class Monster {
}

class Pikachu extends Monster {
    void thunder() {
        System.out.println("Гром!");
    }
}
```
Ошибка: `cannot find symbol` — у типа `Monster` нет метода `thunder`. Если очень нужно, можно привести тип вниз (это называется **приведение вниз, downcasting**) и проверить через `instanceof`:

```java
public class Main {
    public static void main(String[] args) {
        Monster m = new Pikachu();
        if (m instanceof Pikachu) {         // правда ли внутри Пикачу?
            Pikachu p = (Pikachu) m;        // приведение вниз
            p.thunder();
        }
    }
}

class Monster {
}

class Pikachu extends Monster {
    void thunder() {
        System.out.println("Гром!");
    }
}
```
Вывод:
```
Гром!
```
Приведение без проверки, когда внутри другой класс, уронит программу с `ClassCastException`. В лабе приведение вниз не понадобится.

Метод, который принимает родителя, принимает и любого потомка:

## §11. `protected`: «только для своих и наследников»

Вспомни таблицу из §6. `private` — только свой класс. `protected` — свой класс, **наследники** и классы того же пакета.

Зачем это библиотеке. У `Pokemon` методы `setType`, `setMove`, `addMove` — `protected`. Значит:
- в **конструкторе твоего покемона** (он наследник `Pokemon`) их вызывать **можно**;
- из `Main` (он не наследник, и лежит в другом пакете) — **нельзя**.

Авторы библиотеки так сделали специально: тип и атаки покемона — часть его «природы», их задаёт сам класс покемона, а не тот, кто его создаёт. Это снова инкапсуляция.

Как это выглядит, когда классы в разных пакетах (как будет в лабе). Два файла: библиотечный класс в пакете `lib`, программа в пакете `app`:
```java
// файл lib/Creature.java
package lib;

public class Creature {
    protected void addMove(String move) {
        System.out.println("Выучил " + move);
    }
}
```
```java
// файл app/Main.java
package app;

import lib.Creature;

public class Main {
    public static void main(String[] args) {
        Creature c = new Creature();
        c.addMove("Удар");      // ОШИБКА: Main не наследник и в другом пакете
    }
}
```
Ошибка компиляции: `addMove(String) has protected access in Creature`. А если сделать наследника и вызвать `addMove` в его конструкторе — всё работает. Ровно так устроена лаба.

⚠️ В наших упражнениях все классы лежат в одном файле, а значит в одном пакете. Внутри одного пакета `protected` виден всем, поэтому ошибку выше ты в одном файле не увидишь. Она появится только когда классы в разных пакетах.

## §12. Абстрактные классы: как устроены атаки в библиотеке

Что такое «атака вообще»? Её нельзя применить, это только идея: у любой атаки есть тип, сила, точность, и она что-то делает. Применяют **конкретные** атаки: Гром, Удар, Рык. Для таких «общих идей» есть **абстрактный класс**:
- `abstract class Move` — **нельзя создать** объект: `new Move()` — ошибка;
- в нём может быть **абстрактный метод** — без тела, только заголовок с `;`. Каждый потомок **обязан** его написать;
- остальное как в обычном классе: поля, конструкторы, методы с телом.

```java
public class Main {
    public static void main(String[] args) {
        Move a = new Thunder();
        Move b = new Tackle();
        System.out.println(a.describe() + ", сила " + a.power);
        System.out.println(b.describe() + ", сила " + b.power);
    }
}

abstract class Move {
    int power;

    Move(int power) {
        this.power = power;
    }

    abstract String describe();     // тела нет: каждая атака опишет себя сама
}

class Thunder extends Move {
    Thunder() {
        super(110);
    }

    @Override
    String describe() {
        return "вызывает гром";
    }
}

class Tackle extends Move {
    Tackle() {
        super(40);
    }

    @Override
    String describe() {
        return "бьёт с разбега";
    }
}
```
Вывод:
```
вызывает гром, сила 110
бьёт с разбега, сила 40
```

Если потомок забудет написать абстрактный метод, будет ошибка `Thunder is not abstract and does not override abstract method describe() in Move`.

### Шаблон «готовый алгоритм + крючки» — так работают атаки в лабе

В библиотеке у `Move` есть **готовый** метод `attack`, который нельзя менять (он `final`, §13). Он по шагам: проверяет попадание, наносит урон, применяет эффекты. А шаги, которые у разных атак разные, вынесены в отдельные методы-**«крючки»**. По умолчанию крючки ничего не делают. Твоя атака переопределяет только те крючки, которые ей нужны.

Вот упрощённая копия этого устройства. Прочитай внимательно, это модель того, что внутри `Pokemon.jar`:

```java
public class Main {
    public static void main(String[] args) {
        Monster pikachu = new Monster("Пикачу", 35);
        Monster golem = new Monster("Голем", 80);
        Move m1 = new Tackle();
        Move m2 = new Growl();
        m1.attack(pikachu, golem);
        m2.attack(pikachu, golem);
    }
}

class Monster {
    private String name;
    private int hp;
    private int attackLevel = 0;

    Monster(String name, int hp) {
        this.name = name;
        this.hp = hp;
    }

    String getName() {
        return name;
    }

    void takeDamage(int d) {
        hp = hp - d;
        System.out.println("  " + name + " теряет " + d + " HP, осталось " + hp);
    }

    void changeAttack(int delta) {
        attackLevel = attackLevel + delta;
        System.out.println("  атака " + name + " теперь " + attackLevel);
    }
}

abstract class Move {
    private int power;

    Move(int power) {
        this.power = power;
    }

    final void attack(Monster att, Monster def) {      // готовый алгоритм, менять нельзя
        System.out.println(att.getName() + " " + describe());
        if (power > 0) {
            def.takeDamage(power);
        }
        applyOppEffects(def);                          // крючок для эффекта на цель
        applySelfEffects(att);                         // крючок для эффекта на себя
    }

    protected abstract String describe();             // обязательный крючок

    protected void applyOppEffects(Monster p) {        // по умолчанию ничего
    }

    protected void applySelfEffects(Monster p) {       // по умолчанию ничего
    }
}

final class Tackle extends Move {
    Tackle() {
        super(40);
    }

    @Override
    protected String describe() {
        return "бьёт с разбега";
    }
}

final class Growl extends Move {
    Growl() {
        super(0);
    }

    @Override
    protected String describe() {
        return "рычит";
    }

    @Override
    protected void applyOppEffects(Monster p) {
        p.changeAttack(-1);                            // понижаем атаку цели
    }
}
```
Вывод:
```
Пикачу бьёт с разбега
  Голем теряет 40 HP, осталось 40
Пикачу рычит
  атака Голем теперь -1
```

Сравни с библиотекой (подробно в `03`):
| В модели | В `Pokemon.jar` |
|---|---|
| `abstract class Move` | `abstract class Move`, от него `PhysicalMove`, `SpecialMove`, `StatusMove` |
| `final void attack(...)` | `attack` тоже нельзя переопределить |
| `describe()` | `describe()` — текст в бою |
| `applyOppEffects(Monster p)` | `applyOppEffects(Pokemon p)` — эффект на цель |
| `applySelfEffects(Monster p)` | `applySelfEffects(Pokemon p)` — эффект на себя |
| `changeAttack(-1)` | `p.setMod(Stat.ATTACK, -1)` |
| `super(40)` | `super(Type.NORMAL, 40, 1.0)` — тип, сила, точность |

## §13. `final`: «больше нельзя»

`final` значит «окончательный». Работает в трёх местах по-разному:

| Где | Что значит | Пример в лабе |
|---|---|---|
| **класс** `final class X` | от него **нельзя наследоваться** | по заданию все классы без наследников: `Thundurus`, `Golurk`, `Florges` и все 12 атак |
| **метод** `final void f()` | его **нельзя переопределить** | почти все методы `Pokemon` и `attack` у `Move`: чтобы ты не сломал логику боя |
| **переменная/поле** `final int x` | значение задаётся **один раз** | константы |

```java
public class Main {
    public static void main(String[] args) {
    }
}

final class Golurk {
}

class SuperGolurk extends Golurk {
}
```
Ошибка: `cannot inherit from final Golurk`.

```java
public class Main {
    public static void main(String[] args) {
        final int max = 4;
        max = 5;
    }
}
```
Ошибка: `cannot assign a value to final variable max`.

**Константы** пишут как `static final` и именем КАПСОМ: `static final int MAX_MOVES = 4;` Одна на класс (static) и не меняется (final). Пример из Java: `Math.PI`.

⚠️ `final` у переменной-ссылки запрещает **переназначить ссылку**, но не запрещает **менять сам объект**:

```java
public class Main {
    public static void main(String[] args) {
        final int[] arr = {1, 2, 3};
        arr[0] = 100;              // можно: меняем содержимое массива
        System.out.println(arr[0]);
        // arr = new int[5];       // нельзя: переназначить ссылку
    }
}
```
Вывод:
```
100
```

**Вопрос 13.1 (без запуска).** Почему в лабе `Golett` **не** `final`, а `Golurk` — `final`?
<details><summary>Ответ</summary>

От `Golett` наследуется `Golurk`, а от `final`-класса наследоваться нельзя. У `Golurk` наследников нет, а задание требует такие классы делать `final`.
</details>

**Вопрос 13.2 (без запуска).** Чем `final` отличается от `static`?
<details><summary>Ответ</summary>

`final` — «нельзя изменить / переопределить / унаследовать». `static` — «принадлежит классу, а не объекту». Это разные вещи, их можно сочетать: `static final` — константа.
</details>

## §14. Интерфейсы (кратко, в лабе не нужны, но спросить могут)

**Интерфейс** — это список умений без реализации: «кто подписался, обязан уметь вот это». Класс **подписывается** словом `implements` и пишет все методы.

```java
public class Main {
    public static void main(String[] args) {
        Flyer f = new Pidgey();
        f.fly();
    }
}

interface Flyer {
    void fly();          // только заголовок
}

class Monster {
    String name = "Пиджи";
}

class Pidgey extends Monster implements Flyer {
    @Override
    public void fly() {
        System.out.println(name + " летит");
    }
}
```
Вывод:
```
Пиджи летит
```
Методы интерфейса всегда `public`, поэтому в классе пишем `public void fly()`.

| | Абстрактный класс | Интерфейс |
|---|---|---|
| сколько можно | `extends` только один | `implements` сколько угодно |
| поля с данными | можно | нельзя (только константы) |
| конструктор | есть | нет |
| смысл | «является разновидностью» (Гром — это атака) | «умеет» (Пиджи умеет летать) |

## §15. Области видимости переменных

**Область видимости** — где в коде имя переменной можно использовать. Правило простое: **переменная видна от места объявления до закрывающей `}` своего блока.**

| Вид | Где объявлена | Где видна | Сколько живёт |
|---|---|---|---|
| поле объекта | в классе, без `static` | во всём классе | пока жив объект |
| static-поле | в классе, со `static` | во всём классе | всю программу |
| параметр | в скобках метода | во всём методе | пока работает метод |
| локальная | в методе | от объявления до `}` блока | до конца блока |
| переменная цикла | `for (int i = ...)` | только в цикле | до конца цикла |

```java
public class Main {
    static int x = 10;              // поле класса

    public static void main(String[] args) {
        System.out.println(x);      // 10 — поле
        int x = 5;                  // локальная с тем же именем ЗАКРЫВАЕТ поле
        System.out.println(x);      // 5 — локальная
        System.out.println(Main.x); // 10 — к полю можно пробиться через имя класса

        for (int i = 0; i < 2; i++) {
            int sq = i * i;         // sq живёт только внутри цикла
            System.out.println(sq);
        }
        // System.out.println(i);   — ошибка: i тут уже не существует
    }
}
```
Вывод:
```
10
5
10
0
1
```
Для полей объекта (без static) «пробиться» к полю можно через `this.x`, как в конструкторах из §5.

## §16. Пакеты и `import`: раскладываем по папкам

В ЛР1 у тебя был один файл. В ЛР2 будет 19 файлов: 6 покемонов, 12 атак и `Main`. Их раскладывают по **пакетам**.

**Пакет** — это папка с классами плюс «фамилия» для класса. Класс `Thunder` из пакета `moves` полностью называется `moves.Thunder`. Зачем:
- порядок: покемоны отдельно, атаки отдельно;
- не путаются одинаковые имена из разных мест;
- `protected` и «без модификатора» работают по пакетам (§6, §11).

Правила:
1. **Первая строка** файла: `package moves;`
2. Файл обязан лежать в **папке с именем пакета**: `src/moves/Thunder.java`.
3. Класс, который нужен из **другого** пакета, должен быть `public`, и файл называется как этот класс.
4. Чтобы использовать класс из другого пакета, пишешь `import пакет.Класс;` сразу после строки `package`. Или `import пакет.*;` — все классы пакета.
5. Классы из `java.lang` (`String`, `Math`, `System`) импортировать не нужно, они видны всегда.

`import` ничего не «подключает» и не замедляет программу. Это просто сокращение: чтобы писать `Pokemon`, а не `ru.ifmo.se.pokemon.Pokemon`.

Как будет в лабе:
```
programming/lab2/src/
├── lab2/Main.java            package lab2;      import pokemons.*;  import ru.ifmo.se.pokemon.*;
├── pokemons/Golett.java      package pokemons;  import moves.*;     import ru.ifmo.se.pokemon.*;
└── moves/ShadowBall.java     package moves;     import ru.ifmo.se.pokemon.*;
```

Пример из трёх файлов (проверен):
```java

    public String describe() {
        return "пускает угольки";
    }
}
```
```java

import moves.Ember;

public final class Charmander {
    public void useMove() {
        Ember e = new Ember();
        System.out.println("Чармандер " + e.describe());
    }
}
```
```java

```
Вывод: `Чармандер пускает угольки`

**Как сделать в IntelliJ.** Правый клик по `src` → New → Package → `moves`. Потом правый клик по пакету `moves` → New → Java Class → `Ember`. IntelliJ сама напишет `package moves;`. Если используешь класс из другого пакета и он подсвечен красным — Alt+Enter (на Маке Option+Enter) → Import class.

- `:` разделяет пути на macOS и Linux (на Windows `;`).

## §17. `enum`: набор готовых значений

**enum** (перечисление) — тип, у которого заранее известен фиксированный список значений. Например, тип покемона: огонь, вода, трава… Ничего другого быть не может.

```java
public class Main {
    public static void main(String[] args) {
        Type t = Type.FIRE;
        System.out.println(t);
        System.out.println(t == Type.FIRE);
        System.out.println(t == Type.WATER);
        for (Type x : Type.values()) {     // перебрать все значения
            System.out.print(x + " ");
        }
        System.out.println();
    }
}

enum Type {
    FIRE, WATER, GRASS
}
```
Вывод:
```
FIRE
true
false
FIRE WATER GRASS 
```
Значения enum сравнивают через `==`. `for (Type x : Type.values())` — сокращённый цикл «для каждого элемента», работает и с массивами.

В библиотеке три enum'а, ты будешь ими пользоваться:
- `Type` — типы: `Type.ELECTRIC`, `Type.GHOST`, `Type.FAIRY`…
- `Stat` — характеристики: `Stat.SPEED`, `Stat.SPECIAL_ATTACK`…
- `Status` — состояния: `Status.PARALYZE`, `Status.BURN`…

Пишется `Type.GHOST`, точно как `Math.PI`: имя типа, точка, значение.

## §18. Случайность: эффект «с шансом 30 %»

Многие эффекты в варианте срабатывают с шансом: Thunder парализует в 30 % случаев, Shadow Ball снижает защиту в 20 %. Ты уже знаешь `Math.random()` из ЛР1: оно даёт случайное число от 0 (включительно) до 1 (не включительно), каждый раз новое.

Если число меньше 0.3 — это случится в 30 % случаев. Поэтому:
```java
if (Math.random() < 0.3) {
    Effect.paralyze(p);       // сработало в 30 % случаев
}
```
Почему меньше 0.3 — это 30 %: числа равномерно разбросаны от 0 до 1, а отрезок от 0 до 0.3 — это 30 % всей длины.

Если шанс 100 %, `if` не нужен — эффект просто выполняется всегда (как у Low Sweep).

**Четыре принципа ООП одной фразой каждый** (часто просят все четыре):
| Принцип | Своими словами | Пример из лабы |
|---|---|---|
| Абстракция | берём от реального объекта только то, что важно для задачи | у покемона есть тип, 6 характеристик и атаки; цвет глаз не нужен |
| Инкапсуляция | прячем поля, наружу даём методы, объект сам следит за своими данными | поля `Pokemon` закрыты, меняются через `setStats` |
| Наследование | новый класс получает всё от старого и добавляет своё | `Golurk extends Golett`, добавляет одну атаку |
| Полиморфизм | один вызов, а выполняется версия настоящего объекта | `Battle` вызывает атаки, работают твои `describe` и эффекты |

### Мини-квиз

<details><summary>15 вопросов, ответы внутри (сначала отвечай вслух)</summary>

1. **Класс и объект — в чём разница?** Класс — чертёж (тип), объект — конкретная вещь в памяти, созданная `new`.
2. **Что хранит переменная `Pokemon p`?** Ссылку (адрес) на объект или `null`.
3. **Что делает `new`?** Выделяет память под объект, заполняет поля значениями по умолчанию, вызывает конструктор и возвращает ссылку.
4. **Чем конструктор отличается от метода?** Имя как у класса, нет типа возврата, вызывается только через `new`.
5. **Зачем `this`?** Ссылка на текущий объект; `this.name = name` отличает поле от параметра; `this(...)` вызывает другой конструктор.
6. **Зачем `super(name, level)` первой строкой?** Сначала должна создаться часть родителя; у `Pokemon` нет конструктора без параметров, без этой строки будет ошибка.
7. **В каком порядке выполняются конструкторы в цепочке?** От самого старшего предка (`Object`) к потомку.
8. **Перегрузка и переопределение?** Перегрузка — одно имя, разные параметры, выбирает компилятор. Переопределение — потомок пишет свою версию с теми же параметрами, выбирает JVM по реальному объекту.
9. **Зачем `@Override`?** Компилятор проверит, что метод действительно переопределяет метод родителя (защита от опечаток).
10. **Почему `addMove` нельзя вызвать из `Main`?** Он `protected`: доступен наследникам и своему пакету, а `Main` не наследник и в другом пакете.
11. **Почему классы атак `final`?** Требование: классы без наследников запрещено наследовать.
12. **`static` и `final` — разница?** `static` — принадлежит классу, а не объекту. `final` — нельзя изменить, переопределить или унаследовать.
13. **Почему `main` статический?** JVM вызывает его до создания каких-либо объектов.
14. **Что такое абстрактный класс?** Класс, объект которого создать нельзя; может содержать абстрактные методы без тела, которые обязаны написать потомки. Пример — `Move`.
15. **Что делает `import`?** Позволяет писать короткое имя класса вместо полного. Код не подключает и на скорость не влияет.
</details>
